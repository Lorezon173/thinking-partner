# 反馈改进

在阶段整理或用户要求复盘、改善 Skill 时读取。先把当前问题解释清楚，再集中讨论长期改进，不把每条反馈变成即时规则发布。

## 登记与归因

读取本阶段获准反馈和关联片段，分清：

- **明确反馈：**用户说没听懂、理解错了、追问过多或整理干扰等。按原意记录，不把偏好写成普遍真理。
- **可核对错误：**引用不符、遗漏已提供前提、保存失败、恢复错误等。核对实际证据。
- **疑似问题：**模型怀疑步幅太大、过度引导或判断缺少依据。标待核实，不凭猜测诊断用户。

相同根因只是候选合并依据，保留各次发生的引用。正常开放问题、用户改变兴趣、尚无资料或主动跳过检查不自动记作失败。无问题就如实记录，不为证明迭代流程而制造案例。

区分事实知识错误、解释/互动问题、用户个体偏好、记录错误和宿主限制。前者要核查依据，偏好不自动推广，宿主问题不靠堆提示解决。把可观察现象、原因假设和已核实原因写清楚。

## 集中审阅

每个值得改的项目写一个短条目：

> 原问题与引用 → 影响 → 原因及不确定性 → 建议改变什么 → 预期收益/可能损失 → 怎样验证。

优先选对当前体验影响最大的少量改动，避免长反馈清单压过讨论。用户可以接受、修改、暂留或拒绝。当场修正解释不需要等到审阅结束；修改正式 Skill、共享模板或全局规则需要明确批准。普通的“这次好多了”不视为允许修改所有规则。

## 试验、验证与发布

- 提炼修订的案例和验证修订的案例分别列出。不要把原失败样本重做成功当作独立验证。
- 对新例使用相同或可解释的模型、材料和条件，记录 Skill 版本与环境差异；没有取得新例就标未验证，不虚构效果。
- 检查改进是否损害直接回答、停问、允许跳过与正确表达不确定性。一次改一个主要行为更容易解释变化，但不要为形式拆开不可分的修复。
- 结果列为改善、未改善、不确定或引入新问题，并保留失败。用户能解释自己的新增理解才是任务内证据；对话时长、保存数量和选项点击不证明认知提高。
- 修订获准后按当前仓库或宿主资产流程实施，保留版本、批准范围、变更与验证引用。能力不足则交付补丁建议，不能声称正式版本已更新。

项目反馈默认留在项目。将真实材料用于共享样例、跨项目规则或发布包需要另外明确范围；优先用不包含用户隐私的虚构示例验证通用改动。
